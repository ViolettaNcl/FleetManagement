# Backend operations V1

The local ASP.NET Core API now persists maintenance entries, driver shifts and vehicle reservations in SQLite or SQL Server. Routes under /api/operations: GET policy, maintenance, shifts, reservations; POST maintenance, shifts, reservations; DELETE shifts/{id}, reservations/{id}. GET requires FleetRead, writes require FleetWrite. All times accepted as DateTimeOffset and normalized to UTC. Maintenance costs in EUR, at most two decimal places; null means unknown. Existing POST /api/vehicles/{id}/service now records scheduled service through the journal. Work and interval reset plus audit commit in one SaveChanges. Standard trip creation/edit and recommendation account for reservations; strict coverage controlled by Fleet__RequireShifts=true (default false). Existing assignments remain unchanged. Deletion guards protect operational history; audit captures entity/action/actor, not notes. SignalR continues to notify after successful writes.

**Database compatibility:** fresh V3 databases use EnsureCreated as before. Existing V2 databases require the explicit additive upgrade described in [database upgrade](database-upgrade.md). Stop all writers, take and verify a backup, then set Fleet__InitializeDatabase=true and Fleet__UpgradeV2Schema=true for one startup. No automatic upgrade, no deletion or reset. The old default connection remains unchanged.

Single API process only: existing write gate serializes read/validate/save across its requests. No multi-instance transaction guarantee; reads may span multiple queries. Browser demo remains independent, no automatic sync. Strict mode is server configuration, not browser preference. No external API, regulatory compliance or real GPS. Integration CI exercises both providers and restart persistence.

## Batch endpoints
POST /api/operations/batch/preview with {"requests":[...]} returns three strategy results without mutation. POST /api/operations/batch/apply accepts {"confirmed":true,"assignments":[...]} using the selected preview assignments; every request contains ID, origin, destination, offset-aware start/end and distance; each assignment contains request, vehicleId and driverId. Explicit confirmation required. Server revalidates all proposed trips, allocates IDs under the existing write gate, then writes the entire subset and audit rows using a single transactional SaveChanges. A conflict returns 409 without partial insertion. Read-only preview may become stale. Integration tests exercise concurrent submissions within one API process, reject a partially invalid plan, and check restart persistence. No durable request idempotency key, database-level distributed lock or multi-instance guarantee. Preview is not a trusted authorization token; client assignments are fully revalidated at application.
