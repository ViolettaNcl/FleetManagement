# Backend operations V1

The local ASP.NET Core API now persists maintenance entries, driver shifts and vehicle reservations in SQLite or SQL Server. Routes under /api/operations: GET policy, maintenance, shifts, reservations; POST maintenance, shifts, reservations; DELETE shifts/{id}, reservations/{id}. GET requires FleetRead, writes require FleetWrite. All times accepted as DateTimeOffset and normalized to UTC. Maintenance costs in EUR, at most two decimal places; null means unknown. Existing POST /api/vehicles/{id}/service now records scheduled service through the journal. Work and interval reset plus audit commit in one SaveChanges. Standard trip creation/edit and recommendation account for reservations; strict coverage controlled by Fleet__RequireShifts=true (default false). Existing assignments remain unchanged. Deletion guards protect operational history; audit captures entity/action/actor, not notes. SignalR continues to notify after successful writes.

**Database compatibility:** fresh V3 databases use EnsureCreated as before. Existing V2 databases require the explicit additive upgrade described in [database upgrade](database-upgrade.md). Stop all writers, take and verify a backup, then set Fleet__InitializeDatabase=true and Fleet__UpgradeV2Schema=true for one startup. No automatic upgrade, no deletion or reset. The old default connection remains unchanged.

Participating V3 fleet writes use a database transaction and provider lock (SQLite writer reservation or SQL Server transaction-owned application lock), in addition to a process-local semaphore. This protects read/validate/save and ID allocation across cooperating instances. Readers may span multiple queries; direct database writers, older API versions and startup migration must not run concurrently. SignalR has no distributed backplane. Browser demo remains independent, no automatic sync. Strict mode is server configuration, not browser preference. No external API, regulatory compliance or real GPS. Integration CI exercises both providers and restart persistence.

## Batch endpoints
POST /api/operations/batch/preview with {"requests":[...]} returns three strategy results without mutation. POST /api/operations/batch/apply accepts {"confirmed":true,"assignments":[...]} using the selected preview assignments; every request contains ID, origin, destination, offset-aware start/end and distance; each assignment contains request, vehicleId and driverId. Explicit confirmation required. Server revalidates all proposed trips, allocates IDs under the existing write gate, then writes the entire subset and audit rows using a single transactional SaveChanges. A conflict returns 409 without partial insertion. Read-only preview may become stale. Integration tests exercise concurrent submissions within one API process and across two independent processes for standard trip/reservation writes, reject a partially invalid plan, and check restart persistence. No durable request idempotency key; the database write lock coordinates participating V3 instances only. Preview is not a trusted authorization token; client assignments are fully revalidated at application.

## Connected workspace
Open http://127.0.0.1:5095/console on the local API. Embedded HTML, JS and CSS use same-origin requests, Identity sign-in and memory-only access token. It reads fleet, trips, maintenance, shifts, reservations and admin audit; authorized roles can record work and create shifts/reservations with explicit confirmation. All server checks remain authoritative. Manual refresh; no browser LocalStorage token, external service, cross-origin configuration or automatic synchronization with the offline demo. Trip editing and batch apply are API-only for now.

Dedicated Connected workspace CI launches a fresh SQLite API and exercises the actual UI using Playwright: failed/successful login, authorized work/shift/reservation creation, literal text rendering, admin audit, viewer read-only mode, mobile viewport and sign-out/reload. This is separate from the offline Pages demo test.

## Server financial reporting
POST /api/reports/finance/summary and /api/reports/finance/excel use the shared C# cost/budget calculations with inclusive UTC date range, rates, budget and fixed allowance. Both require FleetRead, including Viewer. The connected finance tab calculates and downloads a four-sheet workbook. Recorded work costs remain separate from allowances. Rates are user-entered estimates. No accounting or transactional read snapshot.

Connected Trips now supports confirmed creation and future-trip editing with optional expected-record comparison under the write lock, plus session-local batch requests, preview and confirmed apply. The API returns 409 on an edited record mismatch. Legacy clients that omit expected remain compatible and do not receive lost-update protection. No automatic deletion or retry; server validates all assignments.

Connected change monitoring polls the authenticated database audit revision every ten seconds while the page is visible. It detects committed changes across cooperating instances and prompts manual refresh; it never overwrites unsaved forms automatically. Revision is not a complete change feed and depends on retained audit rows; Identity-only changes are outside this signal. Existing SignalR API remains available. No browser SignalR client or distributed backplane is introduced by polling.

Connected workspace has a session-local English/Russian switch for static interface labels, table headers and common client messages. Canonical work categories and form values remain English on the wire; user-entered data is never translated. Server validation errors, raw audit enums, strategy identifiers and exported workbook contents remain English. Offline Blazor localization is separate and not complete.

Connected register supports confirmed edits with original-value comparison under the database write lock; legacy callers may omit expected values. Admin Accounts lists paged minimal account metadata and creates Dispatcher/Viewer accounts using existing Identity endpoint. No password hashes, tokens, role mutation, password reset or user deletion. Account changes are not included in fleet audit revision. No new admin creation via UI.

Connected Dashboard reads /api/operations/overview (server-clock trip/service counts, 7-day departures, rule-based alerts) and Calendar reads /api/operations/calendar?from=YYYY-MM-DD&days=7 (1–31 UTC days, trips/reservations/shifts/service deadlines). Both are FleetRead; separate queries are not a transactional snapshot. Charts use native progress elements and no external dependencies. No live GPS.

Batch apply supports optional Idempotency-Key UUID. Successful responses are stored atomically with trips and audit, scoped to actor/key. Exact typed payload replay returns original 201 JSON and Idempotency-Replayed: true, without re-insertion or duplicate SignalR. Changed payload with same key returns 409. Receipt cap 50,000, no automatic expiration/deletion. Older callers without key retain previous semantics. See [batch receipts](batch-receipts.md).

Staff-only role change and admin staff session revocation use protected Identity endpoints; self revocation rotates own security stamp. Subsequent bearer-authenticated HTTP requests validate stamp. Connected batch apply retains the same key and body in memory on ambiguous failures, forbids changing pending payload, and can retry the same selection. Reload/signout loses the pending client key; review register before resubmission. Existing hub connections and in-flight requests may continue until expiry/completion.

Connected workspace has a narrow same-origin SignalR JSON Long Polling subscriber for FleetChanged (no generic hub calls, no bearer in URL). It negotiates, handshakes, keeps alive and reconnects with bounded backoff; authenticated revision polling remains the fallback and detects cross-instance changes. On notification it checks the revision and offers explicit refresh without overwriting forms. Session exit aborts transport; revoked credentials are rejected on subsequent HTTP polls. No WebSocket client, distributed backplane or delivery guarantees.

Server ID allocation for vehicles, drivers, trips (including batch), shifts and reservations uses the maximum of current IDs and retained fleet audit entity IDs under the provider write lock. It avoids reusing deleted identifiers in supported databases with intact audit. Maintenance work is append-only. Do not purge or rewrite audit rows; a dedicated persisted sequence would be required before retention cleanup or importing audit-free history. Offline demo still allocates local IDs from current records.
