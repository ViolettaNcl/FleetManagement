# Durable batch dispatch receipts

Clients may send Idempotency-Key (nonempty UUID in D format) on POST /api/operations/batch/apply. Preserve the exact submitted body and UUID until the outcome is known. Server authorization is evaluated on each request, then an actor-scoped receipt is checked inside the same provider transaction lock used for writes. On the first successful submission the trip rows, fleet audit and original JSON response are committed together. A retry with the same typed payload returns HTTP 201 with Idempotency-Replayed: true and no additional writes or change notification. A different payload with that key returns 409. Validation failures do not consume a key.

The original batch format is retained; ordinary fleet writes are also supported as described below. This is not an all-endpoint idempotency framework or a durable queue. All automation clients share the automation actor; separate keys must be used. Receipts may contain historical trip route strings and IDs, and must be protected like the database. Cap: 50,000 receipts; no automatic purge, expiry or in-place edit. Replayed response is historical, not evidence that the trips still exist. Old V3 schemas require explicit upgrade after backup; no destructive migration. Backup includes receipts and restore tests compare rows.

## Ordinary fleet writes
The same optional UUID header covers vehicle/driver/trip create, update and delete, legacy service, maintenance journal creation, shift and reservation creation/cancellation. Existing table and batch fingerprint remain compatible. Ordinary receipts use a versioned method/path/typed-body fingerprint and preserve successful status, JSON and creation Location; no-content deletes replay as 204. All receipts share actor/key namespace and 50,000 limit. Authorization runs before replay; failed validation does not consume a key. Identity mutations and read-only POST reports are excluded. Clients without keys remain request-compatible; the server generates a UUID and stores a durable receipt. No automatic retries or pruning; historical receipts are not current state.

Connected forms use UUIDs for ordinary fleet writes and retain a single uncertain confirmed submission (path, body, key and success handler) in memory. The recovery panel retries that exact request even if a form has been edited. Other ordinary writes and batch apply are blocked until resolved. Definitive client errors clear the pending request; network/5xx uncertainty retains it. Reload/sign-out loses the pending state; inspect server records before resubmitting. Identity changes remain separate.

## Uniform receipt policy
Both batch and ordinary successful writes return the effective `Idempotency-Key` response header (client supplied or server generated). Omitting the request header no longer bypasses actor validation, receipt storage, the shared cap or the write transaction. A client must generate and retain its own UUID before sending to recover safely from a lost initial response; a server-generated UUID cannot be recovered from a response that never arrived. Missing headers remain accepted for legacy clients; malformed, empty, zero or multiple keys fail without mutation. The 50,000-receipt cap now counts successful headerless requests too; plan retention and capacity before sustained use. Existing receipt formats and database schema remain unchanged.
