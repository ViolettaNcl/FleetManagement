# Database concurrency

> Current V6.3 reference: [Engineering handbook](engineering/README.md) · [Русский](engineering/README.ru.md). This specialist document retains historical context; use current code and exact-release evidence for deployment claims.

All FleetStore mutation handlers acquire the process semaphore and then a provider transaction before reading any fleet records. SQLite uses the Microsoft.Data.Sqlite non-deferred serializable transaction, reserving the writer lock before validation. SQL Server uses a transaction-owned exclusive sp_getapplock (fixed resource FleetManagement.FleetWrite.v1, 10 second timeout, public database principal). Both use one outer transaction for validation and SaveChanges/audit; non-success HTTP results roll back. Notification occurs only after commit. Busy/deadlock/lock-timeout failures at the provider are reported as retryable 503 when directly recognized. No blind auto-retry of uncertain commits.

Scope: all cooperating V3 FleetStore writers, including standard trip/vehicle/driver, maintenance, reservation, shift and confirmed batch writes. An old API version, direct SQL or unrelated external software bypasses this protocol; never run it simultaneously. Startup and schema upgrades require all writers stopped. No distributed SignalR backplane, guaranteed snapshot reads or horizontal scalability certification. Supported fleet writes use durable actor-scoped UUID receipts; see [receipt contract](batch-receipts.md). Identity operations use their existing transactions/constraints. SQL Server docs: https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql . SQLite docs: https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/transactions .

CI launches two independent API instances against one disposable provider database and uses synchronized HTTP submissions. Tests expect one success/one rejection for overlapping trips, two distinct IDs for disjoint trips, and one success/one rejection for competing trip/reservation. It also checks both processes see the same register afterward. SQLite contention can be slow; this is a correctness drill, not a throughput benchmark.
